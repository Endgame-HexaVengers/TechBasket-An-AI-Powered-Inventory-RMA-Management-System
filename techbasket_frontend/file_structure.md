# TechBasket Frontend — File Structure

File-based modular pattern for the TechBasket **AI-Powered Inventory & RMA Management System** frontend (Next.js 16.3.1 App Router + React 19 + Tailwind v4 + React Compiler, `@/*` → `src/*`).

> `techbasket_frontend/AGENTS.md` is auto-generated by `next dev` — do not edit it. Read `node_modules/next/dist/docs/` before writing App Router code.

## Pattern

Feature code lives in **feature folders** under `src/features/<feature>/` as flat, named files — one concern per file, mirroring the backend's route / controller / service layering. The `src/app/` route tree stays **thin**: each `page.tsx` only mounts the matching feature's controller; all UI, state, data-fetching, types and Zod schemas live in the feature folder. Reusable, non-feature-specific code lives in `components/`, `lib/`, `hooks/`, `types/`, `schemas/`.

**Per-feature file naming** (only include what the feature needs; `.tsx` only for files that render JSX):

| File | Responsibility |
| --- | --- |
| `<name>.routes.ts` | Route/navigation config for the feature: paths, route guards, sidebar/nav links |
| `<name>.controller.tsx` | Page-level container: orchestrates service calls + state, renders presentational components |
| `<name>.service.ts` | Data + domain logic: API calls, CRUD, transforms (replaces a separate api layer) |
| `<name>.components.tsx` | Presentational UI components (dumb components, no service calls) |
| `<name>.hooks.ts` | Feature-specific reusable hooks (form state, filters) |
| `<name>.types.ts` | Feature-local TS interfaces (mirror backend) |
| `<name>.schema.ts` | Zod validation schemas (mirror backend) |

**Layered flow:** `app/<route>/page.tsx` (thin) → `<name>.controller.tsx` → `<name>.service.ts` → `lib/api.ts` → backend.

**Dependency rule:** controller depends on service + components; service depends on `lib/api.ts`, `types/`, `schemas/`; components are presentational (no service calls); routes depend on the controller; feature files never reach into each other's internal implementation files.

## Standards

- **Service layer:** every feature routes its data fetching through `<name>.service.ts`, which calls the base `lib/api.ts` client; the client unwraps the backend `{ success, message, data }` shape and surfaces `{ success: false, message, errors }` as typed errors. Controllers never call the client directly.
- **Controllers are containers:** `<name>.controller.tsx` owns state + service calls and renders presentational components; markup lives in `<name>.components.tsx`.
- **Validation:** Zod schemas in feature `*.schema.ts` (and `schemas/` for shared inputs) mirror the backend rules — form errors show client-side before submit.
- **Permission-gated UI:** use `usePermission` to hide/disable actions the current role cannot perform (doc §15).
- **Route files stay thin:** a `page.tsx` only mounts the feature controller — never inline business logic; feature-specific paths/guards live in `<name>.routes.ts`.
- **Starter cleanup:** `src/app/components/demo.tsx` is a create-next-app leftover — relocate its content into `components/ui/` or delete during scaffolding.
- **No new runtime libraries assumed:** use native `fetch`, React Context for auth/session; add libraries (state store, form library) only if the team decides.

App shell + sidebar + header → login → admin master data → product list → add/edit product → product details → product approval → purchase → inventory → stock transfer → sales → RMA → reports → AI insights.
